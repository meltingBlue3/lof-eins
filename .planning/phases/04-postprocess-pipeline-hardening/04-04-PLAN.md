<task type="checkpoint:decision" gate="blocking">
  <decision>How to proceed with the validation findings the hard block produces on real production data.</decision>
  <context>
D-01 makes any validation finding block the write, and D-02 makes that unconditional. Against current production data that means the pipeline blocks on every run: planning-time measurement found 390 findings, and Task 1 has now confirmed the live figure and categorised it.

D-08 anticipated exactly this and set the rule for handling it: if the hard block would wrongly halt the pipeline on legitimate data, surface the finding rather than silently loosening D-01. That is why this is a checkpoint and not an implementation decision. Read `04-REAL-DB-VALIDATION.md` before choosing — it has the counts, the distinct-fund spread, and verbatim samples.

The dominant category is open restrictions past the staleness threshold with no matching resume. Some of these are almost certainly real: a fund genuinely suspended for years has no resume to find. Others may be artefacts of how the check pairs resumes, which pops an open restriction on any resume including holiday ones, unlike the interval builder, which deliberately skips holiday resumes. Distinguishing the two is a data-triage question with a real answer in the report, not a preference.

Separately, the phase inherited one pre-existing test failure in the open-ended-limits suite, in loader and engine limit-application logic that REQUIREMENTS places out of scope, alongside 528 overlapping interval pairs in the production output. These are related symptoms and want their own phase.
