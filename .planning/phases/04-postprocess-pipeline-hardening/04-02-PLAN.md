Two defects, one constant, in `src/data/postprocess.py`.

Define a module-level constant `KNOWN_RESTRICTION_TYPES` immediately after the imports and before `load_records`, as a frozenset containing exactly the six values the `subscription_restrictions` CHECK constraint permits: `amount_limit`, `full_suspension`, `holiday_suspension`, `pre_holiday_suspension`, `application_invalid`, `rule_change`. Add a short docstring-style comment recording that this mirrors the CHECK constraint in `src/data/downloader.py` and that the two must be kept in step.

**Fail-loud dispatch (D-06 item 5).** In `build_limit_events()`, before the amount branch at lines 212-222 decides `max_amount`, check the record's `restriction_type`. When it is a non-empty value absent from `KNOWN_RESTRICTION_TYPES`, raise `ValueError` with a message naming the fund code, the effective date, and the offending value. When it is `None` or the empty string, proceed exactly as today — this is the "unspecified" case and 32 records in the production database still carry it after `fix_resume_type()` runs, so treating it as unknown would break the real pipeline. Add the mirror check in `validate()`: for each record with a non-empty `restriction_type` absent from the allowlist, append a finding in the same two-space-indented Chinese format the two existing checks use, naming the fund, the effective date, the action, and the offending value. Both checks are intentional defence in depth — `validate()` runs first inside `postprocess()`, so a real run is blocked with a readable message before `build_limit_events()`'s exception can fire, while the exception still protects any caller invoking `build_limit_events()` directly.

Note for the executor: an unrecognised value cannot be seeded through the harness database, because the `subscription_restrictions` CHECK constraint rejects it at insert time. Exercise this behaviour with in-memory record dicts passed straight to `build_limit_events()` and `validate()`, which is exactly the scenario the guard defends — a widened schema, a hand-edited row, or a future restriction type added upstream without updating this module.

**Inverted-interval clamp (edge: adjacency).** In `build_limit_events()`, the resume-pairing loop computes the interval end as the day before the matched resume. When a non-holiday resume shares the suspend's `effective_date`, that arithmetic produces an end date one day before the start, and the function currently emits the backwards range. Seven such intervals exist in the current production output, and 32 same-day suspend-plus-non-holiday-resume pairs exist in the source records, so this is live corrupt data reaching the backtest. After the end date is computed and before the interval dict is appended, clamp it: when a non-NULL computed end precedes the start, use the start date instead, yielding a single-day interval — the suspension took effect and was lifted within the same day. Leave the NULL open-ended case untouched. Add a brief inline note recording why the clamp exists.

In `tests/test_postprocess.py`, add `TestUnknownRestrictionType` and `TestIntervalOrdering`, both subclassing `PostprocessDBTestCase`, covering every case listed in this task's behavior block. For the determinism assertion, build a record list containing two records for one fund sharing an `effective_date`, call `build_limit_events()` twice, and assert the two returned lists are equal; the guarantee rests on `load_records` selecting ordered by id and Python's sort being stable, so equal keys preserve insertion order.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM-extracted `restriction_type` -> `build_limit_events()` dispatch | The value routes a record to a purchase-amount branch. An unrecognised value silently routing to the wrong branch mislabels a fund's purchasability for the entire interval. |
| `build_limit_events()` output -> `limit_events` -> backtest engine | Interval dates are consumed as trusted fact by PnL computation; a malformed range corrupts results silently. |

Scope note: local single-user pipeline; no network, auth, or session surface. Web threat categories are deliberately omitted.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-04 | Tampering | `build_limit_events()` restriction_type dispatch | high | mitigate | `KNOWN_RESTRICTION_TYPES` allowlist mirroring the database CHECK constraint; an unrecognised non-empty value raises `ValueError` naming it, and produces a blocking `validate()` finding, instead of silently taking the default zero-amount branch. |
