<objective>
Replace `write_limit_events()`'s drop-then-rewrite with a staging table and a single-transaction swap, so a run that dies partway through leaves the previous `limit_events` table intact and queryable.

Purpose: STAB-03. Today the function drops the live table as its first statement and inserts afterwards, so any failure between those points destroys the last known-good dataset the backtest depends on. `ARCHITECTURE.md` flags this as an anti-pattern; this plan removes it.
Output: a transactional `write_limit_events()` staging into `limit_events_new`, and `TestAtomicSwap` proving the failure path is safe.
</objective>

  <action>
Rewrite the body of `write_limit_events()` to stage and swap, per D-04 and D-05. Keep the signature, the parameter names, the docstring's replace-semantics contract, and the final Chinese success message unchanged. Callers need no change.

Open the connection with explicit transaction control rather than the driver's implicit behaviour: set the connection's isolation level to `None` so nothing is auto-committed and data-definition statements participate in the transaction you open. This matters because the driver only opens an implicit transaction ahead of data-manipulation statements, not data-definition ones, so a table drop issued outside an explicit transaction would commit immediately and defeat the whole design.

Inside a `try`, issue an explicit immediate-mode `BEGIN`, then in order:

1. Drop the staging table if it exists. This clears residue left by a hard process kill on a previous run.
2. Create `limit_events_new` with the identical column set, types, defaults, and STORED generated column as the current CREATE TABLE at lines 265-276. Do not create indexes on the staging table — creating them here would require distinct names to avoid colliding with the live table's, and those non-canonical names would survive the rename, because renaming a table in SQLite does not rename its indexes.
3. Insert every event into `limit_events_new` using the same six bound parameters and the same defaulted lookup for `source_announcement_ids` as the current loop at lines 288-302.
4. Only now, with every insert succeeded, drop the live `limit_events` table if it exists, then rename `limit_events_new` to `limit_events`.
5. Create the two indexes on the now-live table under their canonical names, `idx_limit_events_ticker` and `idx_limit_events_is_open_ended`, matching the names currently in the production database.
6. Commit.

Every statement here is a fixed string literal; no table name, column name, or row value is interpolated into a statement string, and all six per-row values continue to travel as bound parameters. The announcement text flowing into the `reason` column is LLM-extracted from third-party PDFs and is untrusted.

In the `except` branch, roll back, then re-raise the original exception unchanged so `postprocess()` and the CLI surface it. Guard the rollback itself: if the failure occurred before the transaction opened, rolling back raises its own error, which must not mask the real one. Because the staging table is created inside the transaction, the rollback also removes it — no separate cleanup is needed on this path. Close the connection in a `finally`.

Verified environment facts, so the executor does not need to re-derive them: the installed SQLite is 3.49.1, which supports transactional data-definition statements, STORED generated columns, and table rename; and no view, trigger, or foreign key anywhere in the production database references `limit_events` — only its own two indexes do, and those are dropped with the table. The rename is therefore safe.

| process lifetime -> transaction boundary | A crash, kill, or unhandled exception can land anywhere inside the write. |
